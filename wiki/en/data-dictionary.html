Data dictionary

Version 0.1 · Chapter 8 of 14 · Updated 18 Nov 2026

Now that you know the modules and elements of the Data model, this chapter describes what to fill in for each one. The data dictionary defines the structure, meaning and completion rules of the data stored on the platform, ensuring consistency and comparability across the data submitted by the different participating centers.

Each field has a formal definition, an expected type and format, a required or optional status and, where applicable, controlled vocabularies or reference ontologies. Some of these fields also make up the ATPBR Identification and barcode system.

Organization of the Data Dictionary#

The data dictionary is organized according to the platform's four main modules:

  • Project:

    • Required fields:
      • Project Title, Acronym, Description, Principal Investigator (PI), Associated Institutions, Ethics Approval, Funding
    • Optional fields:
      • Co-PIs, Scientific Committee, Start Date, End Date
    • Fields linked to ontologies:
      • Associated Institutions (linked to the ROR ID)
    • Fields used to compose the barcode:
      • Acronym (5 to 7 uppercase letters), Associated Institutions (reference to the center that collected the samples)

  • Investigation:

    • Required fields:
      • Investigation Title
    • Optional fields:
      • Description

  • Study:

    • Required fields:
      • Study Title, Associated Investigation, Cancer Type, Description, Specific Ethics Approval
    • Optional fields:
      • Publications
    • Fields with reference ontologies:
      • Cancer Type (linked to OncoTree)
    • Within a single project, each cancer type can have only one Study.

  • Assays:

    • Required fields:
      • Assay Title, Omic Type
    • Optional fields:
      • Description, Associated Repositories
    • Fields used to compose the barcode:
      • Omic Type
    • Field for files already stored at INCA:
      • Associated Repositories: if the FASTQ files are already in the repository of the INCA Multi-user Bioinformatics Platform, enter the absolute path of the directory here (see Data submission).
    • The Assay also states the sharing conditions requested for its data, which are subject to validation and approval (see Data access).

Following the three main elements of the data model of the data ingestion platform, each element has a specific set of clinical, biological and experimental attributes. The full description of all attributes is available in the spreadsheet ATPBR_planilha_metadados.xlsx

Where applicable, each attribute described in this spreadsheet includes:

  • Attribute name
  • Description
  • Data type
  • Required or optional status
  • Allowed values
  • Controlled vocabulary or ontology

Only the main required fields of each element are presented below. The full description is in the metadata spreadsheet.

  • Patients
    • Main required fields:
      • patient_id - Participant code, 4 digits long, defined by the collector center and unrelated to personal data
      • collector_center - Collector center (institution), via the "Collector Center" vocabulary
      • disease_type - The patient's cancer type, chosen from the OncoTree classification among the types of the tissue defined in the Study
      • primary_site - Organ where the tumor originated
      • consent_type - Type of consent obtained for participation in the study
      • data_use_permission - Primary permission for the use of this patient's data/samples
      • data_use_restriction - Additional restriction on data use according to the GA4GH Data Use Ontology (DUO). A single value; use "NRES" when there is no additional restriction
    • Optional field related to the diagnosis: disease_subtype - OncoTree subtype, below the cancer type, when known
    • Automatic field: cid10_category - ICD-10 (CID-10) category calculated by the platform from disease_type, disease_subtype and primary_site. The user does not fill in this field.
    • Fields used to compose the barcode: patient_id, collector_center, cid10_category
  • Samples
    • Main required fields:
      • sample_id - Sample code, 4 digits long, defined by the collector center and unrelated to personal data
      • patient_id - Identifier of the already registered Patient to whom this sample belongs
      • sample_type - Biological material or biological derivative corresponding to the collected sample.
      • sample_status - Pathological classification of the sample at the time of collection.
      • sample_preservation - Method used to preserve the sample after collection.
    • Fields used to compose the barcode: sample_id, sample_type, sample_status, sample_preservation
    • A Sample requires at least one staging system to be filled in (see the section Mandatory Sample Staging, below).
  • Experiments
    • Main required fields:
      • sample_id - Identifier of the already registered Sample from which this experiment was generated
      • analyte_type - Type of analyte used to generate the sequencing data
      • library_kit - Identification of the kit used for library construction
      • sequencing_center - Center where the sequencing was performed
      • sequencing_platform - Identification of the platform used to sequence the samples
      • date_of_sequencing - Date on which the sequencing was performed, in DD/MM/YYYY format
      • library_layout - Type of read used
      • lane_number - Sequencing lane number
      • fastq_1 - Exact name of the read 1 FASTQ file, as listed in the Assay's Data Files
    • Conditional field: fastq_2 - Exact name of the read 2 FASTQ file. Required when library_layout = PAIRED.
    • Fields used to compose the barcode: lane_number. The combination of date_of_sequencing, sequencing_center and sequencing_platform defines the run number (see Identification and barcode system).

Mandatory Sample Staging#

Every sample registered in ATPBR must provide at least one staging system. The platform rejects the registration of a sample that has none of the following fields filled in:

  • FIGO (gynecological tumors)
  • TNM (general system)
  • Rai (chronic lymphocytic leukemia)
  • Binet (chronic lymphocytic leukemia)
  • LMC Phase (chronic myeloid leukemia)
  • AML/ALL Stage (acute leukemias)
  • CIN (cervical intraepithelial neoplasia)

You do not need to fill in all of them: the staging system that applies to the case is enough. The AJCC staging fields are optional and do not count toward this rule. If none of the systems above is provided, the sample is highlighted in the registration table with the message: "Provide at least one staging system (FIGO, TNM, Rai, Binet, LMC Phase, AML/ALL Stage or CIN)."

Dates and time: information as a number of days#

To protect the identity of participants, ATPBR does not accept calendar dates for clinical events, such as date of birth, diagnosis, collection, treatment or death. Combined with one another, these dates would make it possible to re-identify the patient.

Instead, temporal fields take the number of days counted from a common reference point, the diagnosis, which corresponds to day 0. The day of diagnosis is the date of the first exam that concluded malignancy.

Examples:

Field What to enter
diagnosis_age_in_days Patient's age at diagnosis, in days
days_to_sample Days between diagnosis and sample collection
days_to_treatment_first_course Days between diagnosis and the start of the first treatment
days_to_last_follow_up Days between diagnosis and the patient's last record (last follow-up or death)

For example, if the sample was collected 15 days after diagnosis, enter 15 in days_to_sample.

To convert the dates in your institution's medical records, use the date-to-days converter, available in the platform's registration forms. The conversion must be done before filling in the forms, and the original dates must not be sent to ATPBR.

The only calendar date accepted is the sequencing date (date_of_sequencing), because it does not refer to the patient. It must be in DD/MM/YYYY format, with a 4-digit year, be a valid date and cannot be in the future.

Versioning#

The ATPBR data dictionary is kept under version control and updated whenever necessary to accommodate new technologies, omic modalities, clinical fields, reference ontologies and regulatory requirements.

All changes are recorded and documented, ensuring the traceability of changes and backward compatibility whenever applicable.
